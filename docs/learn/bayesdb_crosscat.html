BayesDB + CrossCat: nighttime reading for TRACE

Applied reading · 2026-10-26 (America/New_York) · research cards in BAYESDB_CROSSCAT.md

Remember tomorrow morning. CrossCat is a mixture of mixtures over a table: it partitions columns into independent “views,” and inside each view partitions rows into clusters. BayesDB / BQL is a query layer on top of that kind of generative model — not a replacement for TRACE’s OT game. The TRACE hook is the feature partition × row clusters story for composition vs response, glass-box and nonparametric — not adopting the full Bayesian database stack.

1. Why these two repos tonight

You asked to save probcomp/BayesDB and probcomp/crosscat for later and to get a review page for tonight. They are MIT Probabilistic Computing Project work on tabular joint modelling without neural nets.

  • CrossCat — the structure-discovery / joint-density engine (column partitions × row clusters).
  • BayesDB — the product framing and query language (BQL) for asking “probable implications” of a table the way SQL asks for facts. The legacy BayesDB repo redirects to probcomp/bayeslite (the implementation that actually lived on).

2. What CrossCat found / does

Cite first: Mansinghka, Shafto, Jonas, Petschulat, Gasner & Tenenbaum (2016). CrossCat: A Fully Bayesian Nonparametric Method for Analyzing Heterogeneous, High Dimensional Data. Journal of Machine Learning Research 17(138):1–49. Also arXiv:1512.01272 (submitted 2015-12-03). Earlier workshop framing: “cross-categorization” for multiple overlapping clusterings.

Claims (from the paper, not hype)

  • Estimate a flexible joint over mixed-type table columns without fixing a single clustering for every variable.
  • Discover independencies between variables (outer partition into views) while still using mixture models inside each view for multi-modal dependence.
  • Support efficient conditional simulation / density evaluation for prediction, imputation, and pairwise dependence probabilities.
  • Scale empirically to heterogeneous tables on the order of ~10 million cells in the JMLR experiments (voting records, handwritten digits, gene-expression subsets, and other public tabular sets named in the paper).

Setup in one picture

Think of a data table with rows = entities and columns = variables.

  1. Outer CRP / DP over columns → partition variables into non-overlapping views. Variables in different views are modeled as independent given the latent structure.
  2. Inner CRP / DP over rows, per view → a separate clustering of entities for that view’s variables.
  3. Type-specific component models inside each (category, column) cell — e.g. Beta–Bernoulli for binary, Normal–Gamma for continuous, Dirichlet–Discrete for categorical (paper §2).

Inference: collapsed / auxiliary-variable Gibbs over view assignments, row categories, and hyper-parameters (paper §2.4). Predictions average (or sample) over approximate posterior samples.

Results & limitations (honest)

  • Results the paper actually reports: latent structures that match domain intuition on several public tables; competitive imputation / prediction vs mixtures, Bayes-net structure learning, and some model-free baselines on the tasks they chose; resistance to “distractor” columns that swamp a plain mixture (paper §2.6, §3).
  • Limitations: approximate MCMC (not a closed-form fit); runtime grows with rows × dims × views × categories; single-site Gibbs can need many parallel chains; component models are classical conjugates, not arbitrary response surfaces; modern packaging / CI is aged (see bitrot above). CrossCat discovers column partitions and row clusters — it does not speak Wasserstein or TRACE’s channel game.

3. What BayesDB / BQL adds on top

Cite first: Mansinghka, Tibbetts, Baxter, Shafto & Eaves (2015). BayesDB: A probabilistic programming system for querying the probable implications of data. arXiv:1512.05006 (submitted 2015-12-15).

Plain language: SQL answers “what is in the table?” BQL answers “what does the table make probable?” by Bayesian model averaging over an implicit ensemble of multivariate models (CrossCat-style factorial mixtures are the default baseline meta-model in that paper).

  • BQL primitives (paper): SIMULATE, INFER, ESTIMATE — simulate plausible rows, impute, and estimate dependence / similarity — alongside ordinary SQL-style selection.
  • Generative population model (GPM) interface — any backend that can simulate and score conditionals can plug into BQL.
  • MML — a small meta-modeling language for qualitative dependence constraints and mixing custom models with the automatic baseline.

Repo map: probcomp/BayesDB is the old landing page; probcomp/bayeslite is “BayesDB on SQLite” (BQL interpretation + storage). bayeslite’s README is blunt: expect shifting behavior; do not expect secure data handling; smoke tests via ./check.sh.

For TRACE tonight: treat BayesDB as the query / UX layer idea and CrossCat as the structure idea. We are not building a Bayesian database, and we are not merging bayeslite.

4. Core math / intuition

Chinese restaurant process (CRP) reminder — sequential seating that induces a partition with concentration \(\alpha\):

\[ Pr(z_i = j) \propto \begin{cases} \alpha & \text{if \(j\) is a new table}\\ m_j & \text{otherwise ( \(m_j\) = size of table \(j\) )} \end{cases} \]

CrossCat stacks two levels (paper §2.1, generative process):

\[ \begin{aligned} \alpha_D &\sim \mathrm{Gamma}(1,1), & z_d &\sim \mathrm{CRP}(\alpha_D) && \text{(column → view)} \\ \alpha_v &\sim \mathrm{Gamma}(1,1), & y^v_r &\sim \mathrm{CRP}(\alpha_v) && \text{(row → category | view \(v\))} \\ x_{(r,d)} &\sim L_d(\theta^{d}_{y^{z_d}_r}) &&&& \text{(type-specific likelihood)} \end{aligned} \]

Predictive implication. To sample \(X_{\mathrm{target}} \mid X_{\mathrm{given}}\): for each posterior sample, assign the new row to a category in each relevant view given the observed cells, then draw targets from that category’s component models; average across samples (paper §2.5). Pairwise dependence can be read off as the posterior probability that two columns share a view.

Intuition to sleep on. A plain DP mixture forces one clustering of rows for all columns — so a strong signal in one block of features can drown another. CrossCat’s outer partition lets composition-like structure live in one view while response-like structure lives in another, each with its own row clustering. That is the mixture-of-mixtures / feature-partition story.

5. What this means for TRACE

TRACE’s board problem (RC2 / H7 composition cells): averaging quantile curves is not the same as the mixture of people. Faraday’s survey already pointed at Eulerian \(Q_{\mathrm{mix}}\) numerics. CrossCat is a different angle on the same family of mistakes: assuming one latent grouping explains every column.

Assumptions we would inherit if we borrowed the idea

  • Table = rows × typed columns; missing cells OK in their model.
  • Dependence structure is a partition of features (hard views), not a dense graph.
  • Within a view, a nonparametric mixture is rich enough for the joint.
  • Inference is MCMC over discrete partitions — glass-box latent state, not a net.

What we might borrow (hooks, not a port)

  1. Feature partition for composition vs response. Treat “who is in the population” features and “how the outcome responds” features as candidates for different views — so composition shifts and structural shifts are not forced through one clustering.
  2. Per-view row clusters as glass-box mixture weights. Inside a composition view, category masses \(\pi_c\) are explicit; a change in \(\pi\) is exactly the mix-driven story TRACE needs to book beside CFM.
  3. Posterior dependence as a diagnostic. Column co-assignment probability is a readable “do these features share a signal?” check before trusting a single additive TRACE decomposition.

What we will not do

  • Adopt BayesDB / bayeslite / BQL wholesale as TRACE’s interface.
  • Vendor CrossCat’s C++/Cython stack into the Rust core.
  • Replace TRACE’s OT / L-moment channel game with CRP Gibbs.
  • Use neural nets, or claim CrossCat “solves” H7 without a TRACE-native check.
  • Start a V5 scored suite or Eulerian \(Q_{\mathrm{mix}}\) experiment from this page alone.

6. How we’ll know a borrowed idea worked

High-level falsifiers only (no full suite tonight):

  1. Partition sanity. On a synthetic table where composition features are independent of response features by construction, a CrossCat-style outer partition (or a TRACE analogue) should put them in different views with high posterior probability; a single global clustering baseline should look worse on held-out conditional log score.
  2. Mix masses move shape. If only category weights \(\pi_c\) change between periods (locations fixed), TRACE’s composition / mixing term should move when those masses are wired in; if it stays flat while CFM moves, the borrow failed.
  3. No silent merge. Any prototype stays out-of-core (Python notebook or a thin experiment crate). Merging foreign code into traceot still needs an explicit ask.
